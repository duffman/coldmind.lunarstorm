# cminject decisions

- **Three decorator modes are first-class:** legacy (`experimentalDecorators` + `reflect-metadata`), TC39 standard, and decorator-free (`static $injectable`, `$inject`, `$members`). All three write one `ClassDescriptor`.
- **`reflect-metadata` is a first-class dependency** for browser and Node. Core imports it.
- **A supplied instance is owned** unless `registerInstance` says `external`; `clearInstances` keeps supplied instances either way, and disposes and drops what the container built.
- **`onReady` runs once per instance** per container.
- **No ambient async storage in core.** Resolution context is passed explicitly, so core runs in browsers. The current server import still installs a process-global resolution source; per-root ambient attachment remains pending under item 2.3/G06.
- **Typed tokens:** `createToken<T>()` brands a symbol with its service type. String tokens are `unknown`.
- **Lazy request services:** request and scoped services build on first resolve. `eagerRequest` opts into eager start.
- **Multi shadowing:** a single registration nearer than a multi registration shadows it. A multi at or below the single's owner is a conflict.
- **String-token keys are retained, released or publicly pinned.** Internal lookups do not intern missing strings. Bindings retain their token, declared dependencies and cached dynamic keys across fast/general registration, replacement staging and rollback; final unregister/disposal releases them. `clearTokenCaches()` collects only unpinned zero-reference keys, and `getTokenCacheSize()` reports live interned entries. Public `normalizeToken`, `getGlobalToken` and other raw-key exposures pin the exact issued keys permanently so caller-held symbols remain valid.
- **Diagnostic logs are bounded** (10k entries, trimmed in batches). Historical graph diagnostics retain their string keys until eviction or disposal, including staging/rollback ownership. Internal graph traversal and name-only inspection do not accidentally pin keys; public raw-key graph/interceptor/tracking results deliberately pin only what they expose.

## Replacement isolation

Replacement is an exclusive transaction across one container hierarchy, matching the whole-scope rollback snapshots. New asynchronous resolutions queue until commit or rollback; existing resolutions (including nested and multi builds) drain before staging starts. Candidate and dependent rebuilds carry the transaction's explicit staged context and do not queue behind their own lock. Competing replacements serialize and select their current binding after admission. Synchronous cache reads during replacement throw `LifecycleError`; synchronous registry mutations conflict rather than changing the frozen graph. Disposal remains able to cancel replacement and release queued callers. This boundary does not claim to drain application code already holding returned instances, and is not a path-local lock.

## Factory parameter is a resolution-bound view

A factory receives a resolution-bound view of its owning container whose resolution methods carry the current path, chain and waits-for build. It is not reference-equal to the container: compare `identity.id`. G04 replaced generated forwarding in place with an explicit `ContainerView implements IContainer`, including generic overloads, getters/setters and direct delegation using the actual target receiver. Factory/completion subclasses preserve contextual resolution/construction and stable originating signals. One-way prototype attachment preserves `instanceof Container` and logical identity without prototype method transplants. Typed operation callbacks are allocated once per container. G05 has now extracted and independently reviewed that boundary in `cminject.view.ts`; the final responsibility-level coverage-floor mapping has passed without lowering any original floor.

Once the build finishes (after `onInit`), a retained factory view resolves from a fresh root context, so a singleton that keeps its parameter does not carry a stale path into later resolves.

## Per-tree completion and retry

Completion state is root-owned and weakly keyed by instance, shared by descendant scopes but not unrelated roots. Pending completion is distinct from successful completion: ordinary concurrent callers join the full pending operation, failures permit retry, and successful member/wrapper/hook stages are retained so retries do not stack wrappers or rerun successful hooks. Separate roots apply their own completion while retaining original method provenance. A shared mutable instance is not copied; its fields reflect the last successful root injection.

Each instance hook receives an explicit live attempt-local context through `context.container`. Use that container for hook operations, including after `await`. Valid contextual reentry is idempotent and does not await the hook itself; unrelated callers still wait for full completion. Hook links expire on success/failure and retries receive distinct identities, so retained stale contexts cannot bypass retry work.

A captured bare root does not carry hook lineage. Awaiting that root's pending completion from the same hook after suspension is an unsupported user-promise self-cycle, not a claimed ambient-context feature. Standalone member injection is not implicitly covered by a factory deadline or server ambient context.

## Promise API boundaries

Promise-returning entry points reject rather than synchronously throwing when thenable shielding cannot represent a frozen/unshieldable service value. Synchronous reads preserve the actual frozen instance. This keeps the async API's rejection contract without silently replacing service identity.

## Build deadlines, signals and disposal

`buildTimeout` accepts finite nonnegative milliseconds, `undefined` to inherit (off at a root) and `null` to disable explicitly. Registration `timeoutMs` overrides the routed owner's policy and is preserved by replacement. Invalid settings throw `RangeError`. Zero schedules a next-turn asynchronous deadline; an entirely synchronous graph stays synchronous. Large finite delays are segmented against an absolute monotonic deadline rather than overflowing native timers; timers are unrefed and cleared on every terminal path.

Every async materialization, including transients, shares one controlled terminal outcome across the first caller and joiners. The deadline covers factory and `onInit`; `DI_BUILD_TIMEOUT` includes pending builds, waits-for edges and resolution path. Ownership determines policy: a root-owned singleton does not inherit a requesting child's deadline or get cancelled merely because that child is disposed.

Container disposal marks/cancels/aborts the full owned subtree with `DI_BUILD_CANCELLED` before awaiting teardown. Uncooperative user promises cannot hold container disposal open. Cancellation cannot forcibly interrupt JavaScript: produced, unreturned owned values are cleaned exactly once when their user factory/initializer settles; late rejections are consumed and external values are never disposed. Successfully returned ordinary transients remain caller-owned. Terminal rollback does not reinstall registrations, records or diagnostic history into ended scopes and cleans detached owned originals in reverse disposal order without reviving them.

A factory/initialization/completion facade retains its originating build signal identity after resolver or hook-lineage expiry. Ready and successfully returned transient signals still abort when their owner is disposed, without making transient values lifecycle-owned. Standalone manual completion receives a scope-lifetime signal, not an automatic build deadline. Native `AbortSignal.any` combines build and owner signals; without it, the fallback requires `WeakRef` and `FinalizationRegistry`, removing source listeners on abort or collection. Supported Node/Bun floors supply native `any`; missing both composition mechanisms produces `LifecycleError`.

`DiRuntime` graceful lease draining remains separate: runtime drain waits for active leases and does not forcibly abort arbitrary leased application work. Scope teardown cancellation applies when actual container disposal begins.

## Public types and decorator expressibility

`Constructor<T>` and `AbstractConstructor<T>` use `never[]` as a safe token constraint, not a requirement that consumer classes have zero constructor parameters. Required-argument classes and abstract tokens retain inference; actual arbitrary-argument construction uses a documented `Reflect.construct` boundary. Production source has no explicit `any` syntax or double assertions. Remaining internal assertions have local invariant reasons; the G04 inventory records them rather than claiming all assertions were removed.

Public handles are backed by `TypedBinding<T, D>`, which genuinely implements `BindingHandle<T, D>`; this does not add a public binding implementation API. Internal registry storage erases the public replacement payload signature through an operational type and recursive links, not a claim that all generic handles are interchangeable. Plain registrations keep their allocation-free handles.

`ServiceFactory` uses a non-distributive argument tuple with explicit caller-any detection. Default `void`, explicit `undefined` and `void | undefined` retain a one-parameter container-only call shape. Other data types, including unions containing `undefined`, retain a required data slot. An explicitly caller-supplied `any` data parameter also retains the historical required payload call shape; production declarations need no own `any` syntax to preserve that compatibility. Lifecycle factories follow the same rule.

Decorator types now expose actual legacy/TC39 placement overloads instead of an arbitrary-call signature. Registration aliases are class-only; injection aliases target fields, auto-accessors, setters and legacy constructor parameters. Legacy TypeScript's two-argument property-decorator syntax cannot structurally distinguish a method from a function-valued field: a legacy `@Inject` method declaration may compile, but the runtime placement guard rejects it. Rejecting every function-valued key would incorrectly remove valid field injection. TC39 placement and explicit legacy three-argument descriptor negatives remain strictly checked; not every invalid legacy grammar placement is statically expressible.
